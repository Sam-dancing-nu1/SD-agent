# survey-dg-ai-notes —— Pi-Agent 源码解读 + 二开实战 设计思想提炼

来源：github.com/buchidonggua/dg-ai-notes（git clone 实读 markdown 原文；渲染版 dg-ai-notes.pages.dev 未另行抓取，仓库即全文）。引用版本：源码解读篇按 pi-coding-agent v0.80.2 行号，实战篇按 SDK v0.83.0。定位：对方走 TS/Python 二开 pi-agent SDK 路线，我们是 Rust 自研底座——**只取设计思想，不引其代码与 API**。本文件属调研类，保留来源名称供溯源。

## 0. 结论速览（先看这里）

1. 整站最有价值的不是 API 用法，而是三条设计主线：**内核极简 + 叠加可选**（Agent Loop）、**两层消息/两类事件的边界设计**（内部丰富、LLM 严格；观察不等、干预必等）、**多层兜底的上下文工程**（截断/组装/压缩/分支摘要四层互补）。
2. 系统提示词的工程方法论是"五段拼装 + 三级回退 + 静态/动态分层"：人设单独一段且必须可整体替换，规则/项目上下文/技能清单各司其职，技能走"清单进 prompt、全文按需拉取"。
3. Agent Loop 的终止判断刻意做"笨"：**不判断任务完成度，只看本次输出有无工具调用**（且未被工具批量 terminate）；错误与中止走硬停止快速失败；产品级需求（插队、续任务、切模型、安全阀）全部走钩子叠加，不污染内核。
4. 会话存储拆成"存哪里（介质）"与"长什么样（结构）"两个正交维度；结构选 append-only 树 + 指针移动做回退/分叉，状态变更也节点化，回退天然正确。
5. 对我们的 Rust 底座：可迁移项以"直接可用"居多（循环内核、双层消息、双管道事件、四层上下文防线、append-only 会话树、五步工具管道）；"需改造"集中在 token 估算、缓存策略、扩展加载机制；"不适用"的是其 CLI 产品形态与 TS 生态特有实现（Jiti、声明合并、typebox）。

## 1. 源码解读 10 章：每章"是什么 / 怎么做 / 为什么"

### 第1章 开篇总览
- 是什么：Pi = 极简可扩展的终端编码 Agent 外壳（coding agent harness），TS 编写，MIT，定位"积木而非整车"。
- 怎么做：核心四工具（read/write/edit/bash）+ 三辅助（grep/find/ls）；静态系统提示词约 90 词，运行时拼装后 200-400 词；刻意不做 MCP/子 Agent/计划模式，缺失能力靠五根杠杆自建（扩展、技能、Prompt 模板、上下文文件、Pi Package）。
- 为什么：默认功能越多 = 不可改变的约束越多；把"加法的权力"留给使用者，核心只保下限。对应我们"守住模型能力下限"的定位，立场一致。

### 第2章 三层架构
- 是什么：pi-ai（调模型）→ pi-agent-core（跑循环）→ pi-coding-agent（业务/CLI/SDK），pi-tui 正交独立，另有实验性编排包。
- 怎么做：分层规则不是"禁止跨层引用"而是**依赖方向单向向上**（顶层可直接用底层类型——类型是"原子"，各层都要）；类型逐层递进扩展不回改：Tool（名片）→ AgentTool（+execute/执行模式）→ ToolDefinition（+渲染/提示词片段）。
- 为什么：每层可独立发布复用（只用底层也能调模型）；验证法"去掉上层这层还能跑吗"。与我们一核两壳的分层自检同构。

### 第3章 Agent Loop（详见 §2）
- 是什么：ReAct 循环（Reason→Act→Observe），Trace（agent_start→agent_end 全程）内含多个 Turn（一次模型调用 + 其触发的工具批）。
- 怎么做：内核约十几行 while；stopReason 五值（toolUse/stop/length 来自 API，error/aborted 由流式层兜底注入）；实际驱动是"content 里有 toolCall 且未全 terminate"。
- 为什么："什么时候停"是人类定义的工程约定而非模型决策；把决策外包给模型输出模式，代码只做最简信号判断。

### 第4章 模型调用
- 是什么：一套统一接口调 30+ 供应商（消息格式/流式/思考/缓存四维度全不同）。
- 怎么做：三层——统一入口（查表路由）→ 事件协议（12 种流事件：text/thinking/toolcall 各"start→delta→end"+ done/error，每事件带整条消息快照 partial）→ 每供应商一个翻译器（5 步骨架：建客户端→构请求→发送→译响应流→终止事件）。
- 为什么：差异收口到翻译器，Loop 侧零感知；"partial 全量快照"让消费方原地替换即可，无需拼增量。

### 第5章 工具系统（详见 §2 错误处理）
- 是什么：工具 = 三层类型 + 五步执行管道（参数预处理→Schema 验证→beforeToolCall 拦截→execute→afterToolCall 后处理）。
- 怎么做：prepareArguments 处理各模型参数怪癖（如字符串化数组），与"通用正确性校验"分离；execute 签名一次给全（id/校验后参数/取消信号/进度回调 onUpdate/运行时 ctx）；并行执行三阶段：准备顺序（含权限检查）→ 仅 execute 并行 → result 消息按调用顺序回填；批次内一个 sequential 就整批串行（一票否决）；edit 再加同文件串行队列第二道防线。
- 为什么：90% 的工具工程量在周边（校验/取消/审计/拦截），框架接管；"宁可多等不可出错"。

### 第6章 消息系统
- 是什么：两层消息——内层 AgentMessage（标准 3 种 + 自定义 N 种，结构化存），外层 Message（只 user/assistant/toolResult，发 LLM）。
- 怎么做：convertToLlm 立在边界做"翻译"（默认过滤只留 3 种标准；压缩摘要等译成带 `<summary>` 标签的 UserMessage）；自定义消息经扩展点（空接口 + 声明合并）注册。
- 为什么：同一条数据有两个冲突读者（UI 要结构化字段、LLM 只要扁平文本）——**存结构化、边界翻译**，两边不妥协；额外获得 UI 专用渲染、持久化还原、`excludeFromContext` 精细可见性控制三个能力。

### 第7章 事件驱动（详见 §4）
- 是什么：发布-订阅，10 种内核事件按 4 层嵌套生命周期（Agent→Turn→Message→Tool Execution，各 start/update/end）。
- 怎么做：两条管道共用事件源——订阅管道（只读、不 await、返回值丢弃）与扩展管道（await、读返回值、可拦截/链式改写）；扩展另独占 5 个决策点事件（input / before_agent_start / context / tool_call / tool_result）。
- 为什么："能改行为"的根源是"Agent 停下来等返回值"，不是单独赋权；高频进度事件攒批等、低频生命周期逐个等——越重要的事件等得越严。

### 第8章 上下文工程（详见 §3）
- 是什么：窗口固定 vs 对话无限增长，在输入侧与历史侧共布 4 层防线：工具输出截断、系统提示词组装、Compaction、分支摘要。
- 怎么做：截断双限制（2000 行 / 50KB 先触者胜）+ 双向（read 留头、bash 留尾）+ UTF-8 边界安全 + 落盘逃生通道；提示词 = 多级上下文文件向上递归合并 + XML 包装 + 技能懒加载。
- 为什么：无银弹，每层只解自己的问题互相兜底；上下文工程是"塑形"不是单纯压缩；"拉模式"（清单 + 按需读）比"推模式"（全文塞）省一个数量级。

### 第9章 上下文压缩（Compaction）
- 是什么：对话超阈值时把旧消息换成结构化摘要，**发生在两轮对话之间**（agent_end 后检查，下一轮重建上下文时生效）。
- 怎么做：触发 = contextTokens > window − reserve（含应急：API 溢出报错再压）；token 估算用 chars/4 启发式；切割点从最新往旧累积 keepRecent（约 20K）再落合法切点（排除 toolResult，保证消息对完整）；摘要 6 固定段（Goal/Constraints/Progress(含 Blocked)/Key Decisions/Next Steps/Critical Context）+ 增量更新（旧摘要为 previousSummary）+ 文件跟踪清单（read/modified 跨压缩累积）；切在 assistant 会断 Turn，用 turnPrefix 三段式轻摘要并行补上。
- 为什么：固定模板对抗 LLM 摘要"自由发挥"的遗漏偏差；增量更新防多次压缩的摘要漂移；估算"宁高勿低"（高估无害、低估报错）。

### 第10章 会话管理
- 是什么：存储拆两正交维度——介质（本地 JSONL，一行一 Entry，接口留出可换库）与结构（Session Tree：append-only、认父不认子、leafId 指针）。
- 怎么做：追加 = 新节点 + 移指针 O(1)；回退/分叉 = `leafId = 目标节点`，不删数据；9 种 Entry 按"对 LLM 调用的影响"分三组（进上下文 4 / 改状态 2 / 纯元数据 3）；buildSessionContext 从 leaf 回溯 root 压扁成线性 messages，状态变更（切模型/思考档）沿路径覆盖式提取；压缩用 firstKeptEntryId 做"选择性收集"视图，非破坏性。
- 为什么：回退/重试/分叉要求"不丢数据的撤销"；状态节点化让回退天然正确（回退到切换前的路径，状态自动还原）；JSONL 行级 append 与 append-only 树完美契合；延迟落盘（首条 assistant 前攒着）避免"有问无答"半截会话。

### 附：第11章 扩展系统（设计文档，未出正章）
- 核心机制：8 个工作流关键点 emit 事件 + 事件总线，用"约定（事件名 + 返回值协议）"换"灵活（不改源码）"；四种介入模式：通知 / 取消（返回 cancel）/ 修改（链式 transform）/ 短路（block）。
- 两个精妙点：① 两阶段绑定——工厂函数在加载期执行时操作型方法是 throwing stubs，Agent 就绪后 bindCore() 整体换成真实现，化解"注册太早 vs 要操作运行时"的时机矛盾；② 防御——错误隔离（handler 全 try/catch，唯 tool_call 例外：崩了即拦，fail-closed 宁可错杀）+ API 门面三层最小权限（注册面 / 只读上下文 / 特权命令面，危险能力不外露）。

## 2. 重点一：系统提示词设计方法论（实战第4章完整提炼）

**框架默认注入什么（五段拼装）**：最终提示词 = ① 基础人设 + ② 追加规则 + ③ 项目上下文（AGENTS.md/CLAUDE.md 向上递归）+ ④ 技能描述（懒加载清单）+ ⑤ 工作目录一行。做垂直智能体**只有 ① 必须管**：②③④ 是"自动注入项目知识"机制，不创建对应文件即为空；⑤ 无害可留。

**基础人设三级回退**：代码级 override（可动态拼装）> 项目级 SYSTEM.md 文件 > 框架硬编码默认人设。教程明确反对用全局级 SYSTEM.md（影响机器上所有项目，难追踪）；追加规则可显式清空（返回空集）以免干扰。

**为什么这么分**：
- 人设与规则分离——人设是"我是谁"（唯一必须整体替换的），规则是"怎么干活"（可叠加可清空），两者生命周期和改动者不同（运营改文案 vs 工程师改代码）；
- 静态/动态分层——人设/业务规则/输出格式走本地文件（版本管理 diff 清晰、运营可改），用户身份/部门/数据权限走每次请求查库（个性化 + 权限边界明确），会话状态从会话存储读；最后 join 成一段；
- 拼装纪律：每个来源独立获取，"同一智能体内组合角色要素"≠"一个服务装多个人设"——人设完全不同就该拆成多个 Agent 服务；
- 输出格式单独成段（先结论后分析、要点化、每原因附验证方法、末尾行动建议）——把"回答的形状"写成硬约束而非期望。

**配套细则**：技能清单只放 name/description/location + 一句"任务匹配时用读取动作载入全文"的契约；元数据（当前日期、cwd）放提示词**末尾**；项目上下文 XML 标签带 path 属性以区分规范层级优先级。

## 3. 重点二：Agent Loop 循环控制

- **终止条件（三级）**：① 正常停——本次输出无 toolCall（或批次工具全 terminate，用 every 不用 some），且无插队/追加消息；② 硬停止——error/aborted 立即发 turn_end+agent_end 返回，不查追加队列（fail fast）；③ 外部安全阀——shouldStopAfterTurn 钩子（上下文快满、达最大 Turn 数）返回 true 即停。
- **工具调用**：一批 toolCall 同 Turn 执行（并行三阶段 / 一票否决串行）；结果统一为 ToolResultMessage（toolCallId 精确关联回调用）；**所有错误同构**——工具未找到/参数预处理炸/校验不过/被拦截/execute 抛异常/后处理炸，六种出口全部收敛为一条 isError:true 的消息，绝不让异常逃出管道打断循环，由模型读错误自行决定下一步。
- **叠加设计（内核外的洋葱层）**：steering 紧急插队（每圈开头+结尾查队列，进循环前先查一次防漏）；followUp 追加任务（内层全停后续命重启，同一 Trace 内连续）；prepareNextTurn（Turn 间换模型/上下文/思考档）；shouldStopAfterTurn（安全阀）。内核约十几行，剥掉任何叠加层内核仍可跑——这是"内核有没有被污染"的试金石。
- **流式细节**：先 push 空壳消息再原地替换（UI 逐字渲染）；llmContext 每 Turn 重建 wrapper 防状态污染，但 systemPrompt/tools 引用稳定不破缓存。

## 4. 重点三：上下文工程手法（截断 / 压缩 / 缓存）

- **截断（输入侧，每条工具结果）**：行数+字节双上限先触者胜；read 截头（文件头部信息密度高）、bash 截尾（错误堆栈在尾）；逐字符累计字节保 UTF-8/代理对完整；单行超限取行尾部分并标记；截断必带元信息行（"显示第 X-Y 行，全文在 /tmp/xxx"）给模型逃生通道；grep 独立单行 500 字符限长。
- **压缩（历史侧，阈值触发）**：见 §1 第9章——两轮之间执行、向后累积定切割点、6 段结构化摘要、增量更新、文件跟踪、turnPrefix 补断。
- **缓存**：Anthropic 系在三处打缓存断点——system 末尾、最后一个 tool、**最后一条 user message（rolling cache，随对话推进）**，前缀内容寻址命中；OpenAI 系按 session 键自动前缀匹配；兼容层可复用 Anthropic 式标记。稳定内容（system+tools）在前、变动 messages 在后，是协议层就为缓存设计的排布。
- **加法侧**：多级上下文文件从 cwd 向上递归合并（外通用→内具体，XML 包装带 path）；技能懒加载清单；估算口径 chars/4（英文够用、中文严重低估——已知精度问题，值得我们用真实 tokenizer 或保守系数规避）。

## 5. 重点四：事件订阅两类的用法

| 维度 | 观察类（订阅） | 干预类（扩展钩子） |
|---|---|---|
| 能力 | 只读广播，返回值丢弃 | 可拦截（block）、可取消（cancel）、可链式改写（transform） |
| Agent 是否等 | 不等（同步派发即走） | 等（await 返回值再决策） |
| 独占事件 | 无 | 5 个决策点：input / before_agent_start / context / tool_call / tool_result |
| 典型用途 | 流式渲染、日志、SSE 转发、token 统计、落库审计 | 拦危险工具、改写上下文、替换系统提示词、过滤输入、脱敏结果 |
| 坑 | async 监听器错误被吞，须自己 try-catch；整轮收尾别用 message_end（一轮多次），用每 prompt 一次的 settled 事件 | handler 被 await，落库须 fire-and-forget 入队；tool_call 处理器崩溃 = 拦截（fail-closed）；高频进度事件攒批 |

判断口径一句话：**要不要改变 Agent 行为**——要则走干预类（Agent 等你），不要则走观察类（轻、不拖慢主循环）。

## 6. 对 Rust 自研底座的可迁移清单

对照 concept-v2 十二件组件标注。状态词：直接可用 / 需改造 / 不适用。

1. Loop 内核极简 + 叠加洋葱（终止=输出无工具调用；error/aborted 硬停；钩子叠加插队/续命/切模型/安全阀）→ 直接可用（对应"生命周期钩子与单一调度入口"）。
2. Turn/Trace 两级语义与事件包裹（一个 Turn 恰一次模型调用）→ 直接可用。
3. 双层消息（内结构化 / 边界翻译成三种标准消息；压缩摘要译成带标签的用户消息）→ 直接可用（对应"上下文与成本工程"、记忆系统）。
4. 工具五步管道 + 六种错误统一收敛为 isError 结果消息（永不抛出打断循环）→ 直接可用（对应"能力供给与扩展"）。
5. 工具批次调度：一票否决串行 + 三阶段并行（准备顺序/执行并行/结果按调用序）→ 直接可用。
6. 双管道事件：观察类不等、干预类等+读返回值；决策点独占；fail-closed 拦截；高频攒批低频逐等 → 直接可用（对应"事件、网关与审计（分级事实源）"）。
7. 上下文四层防线（截断/组装/压缩/分支摘要）+ 截断双限制双向 + 逃生通道 → 直接可用。
8. Compaction：阈值 + 两轮之间执行 + 合法切点（不切 toolResult）+ 固定模板摘要 + 增量更新 + 文件跟踪 → 直接可用（对应"上下文与成本工程（前缀冻结）"，我们已有前缀冻结，压缩是互补层）。
9. 会话树 append-only + 认父不认子 + leafId 指针回退/分叉 + 状态节点化 + 路径压扁出口 → 直接可用（对应"工作区与隔离"与记忆系统）。
10. 存储拆"介质/结构"两正交维度；JSONL 行级追加 + 延迟落盘防半截会话 → 直接可用（Rust 侧可用 SQLite/文件，接口先行）。
11. 系统提示词五段拼装 + 人设三级回退 + 静态文件/动态数据分层拼装 + 技能懒加载（清单进 prompt、按需拉取）→ 直接可用（对应"配置档案与认知纪律域"）。
12. 缓存断点设计（稳定前缀在前 + rolling cache 跟随最新 user message）→ 需改造（我们走前缀冻结路线，需对齐自家模型供应商的缓存协议，机制思想可取）。
13. token 估算 chars/4 启发式 → 需改造（中文低估是硬伤；改真实 tokenizer 或按语种加权的保守系数）。
14. 扩展两阶段绑定（throwing stubs → bindCore）→ 需改造（Rust 无运行时热加载 TS 的语境；插件面可改用编译期注册 + 运行时 enable，或脚本引擎，思想是"注册期防误用、就绪后替换"）。
15. Provider 翻译器模式（统一入口查表 + 12 种流事件协议 + 每供应商一翻译器）→ 需改造（我们模型接入面自定协议，但"差异收口到适配器 + 全量快照替代增量拼接"直接可取）。
16. prepareArguments 参数怪癖垫片（与正确性校验分离）→ 直接可用。
17. 会话树分支摘要（LCA 找分叉点、5 段模板、预算收紧 2048、前言声明"这是旁支探索"）→ 需改造（依赖会话树分叉能力，先有 9 再上此条）。
18. 极简产品哲学（默认最少、加法权交给使用者）→ 直接可用（与四公理立场一致，可写进设计依据）。
19. CLI/TUI 产品形态、RPC 模式、Pi Package 分发生态 → 不适用（我们的两壳形态自定）。
20. TS 生态特有实现（声明合并做类型扩展、typebox Schema、Jiti 热加载、npm workspaces）→ 不适用（Rust 用 trait/enum/宏与 cargo workspace 达成同等意图）。
